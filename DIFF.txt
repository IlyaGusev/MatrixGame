Scope: only modules that already have substantive implementation in rust_port.
Pure stubs (renderer/particles.rs, renderer/units.rs, game/ai.rs) are skipped.

1. CAMERA (renderer/camera.rs vs MatrixCamera.cpp)
==============================================================

1.1 Edge-pan trigger distance
    [C++]  MatrixFormGame.hpp:9        MOUSE_BORDER = 4 px
    [RUST] renderer/camera.rs:69       MOUSE_EDGE    = 8.0 px
    Observable: Rust starts edge-panning twice as far from the window
    edge as the original; feels "sticky".
    AP: change MOUSE_EDGE from 8.0 to 4.0 in camera.rs:69.

1.2 Edge-pan is always on
    [C++]  MatrixFormGame.cpp:232-240  edge pan only if !IsArcadeMode()
    [RUST] renderer/camera.rs:349-377  unconditional
    AP: gate the edge-pan branch behind a mode flag once arcade mode
    is introduced; until then, leave a TODO at camera.rs:349.

1.3 FOV convention
    [C++]  MatrixCamera.hpp:51         CAM_HFOV = GRAD2RAD(60)  — name says
           MatrixCamera.cpp:672        "horizontal" but it is passed to
                                       D3DXMatrixPerspectiveFovLH(fov,...)
                                       whose `fov` is the *vertical* FOV.
    [RUST] renderer/camera.rs:27       CAM_FOV = 60° treated as vertical.
    The C++ identifier is misleading but the value it passes to D3D is
    used as vertical FOV, so Rust matches numerically.
    AP: rename CAM_FOV to CAM_VFOV in camera.rs to document intent; no
    numeric change.

2. TERRAIN (renderer/terrain.rs, game/map.rs, game/map_prepare.rs
          vs MatrixMap.cpp, MatrixMapGroup.cpp, MatrixMapPrepare.cpp,
             MatrixRenderPipeline.cpp)
==============================================================

2.1 Texel-center UV offset on atlas sampling
    [C++]  MatrixMapGroup.cpp:341-342  uv = ts_inv * v->tx (corner)
    [RUST] renderer/terrain.rs:225-226 uv = ts_inv * (tx + 0.5)
    Observable: Rust samples half a texel in from the tile corner,
    which changes how filtering picks up the 6-mip atlas — can soften
    seams but also shifts the whole atlas.
    AP: remove the +0.5 bias in terrain.rs:225-226 to match C++; verify
    against screenshots. If the +0.5 is specifically there to mask
    bleed from neighbouring atlas tiles, leave a comment stating so.

2.2 Down-cell flag recomputation per frame
    [C++]  MatrixMapGroup.cpp:314-335  down flag cached into
                                       mp->color (high bit of ARGB).
    [RUST] renderer/terrain.rs:237-250 re-reads CELLFLAG_DOWN and calls
                                       map.normal(vx, vy) each rebuild.
    No observable diff today because BuildBottom is only called at
    load, but map.normal() must always agree with the baked point
    normal for the two to remain equivalent.
    AP: bake the down-flag decision (and the resulting offset
    direction) into the vertex when the group is built, so the draw
    path never recomputes it. Add an assert in debug builds that the
    per-point normal matches the one used at BuildBottom time.

2.3 Group/cluster visibility
    [C++]  MatrixVisiCalc.cpp:534-779  3-D AABB frustum test per group,
                                       bounds = (p0.x, p0.y, m_minz) to
                                       (p1.x, p1.y, m_maxz_obj_robots).
    [RUST] visible_groups_mask (called from water.rs / terrain.rs) —
                                       extent not verified.
    AP: audit visible_groups_mask implementation against MatrixVisiCalc
    to make sure the AABB actually uses the per-group min/max Z from
    loaded map data (not a global map Z), otherwise tall objects at
    map edges can be wrongly culled.

2.4 Projected shadows from buildings/robots onto terrain
    [C++]  MatrixMapGroup.cpp:156-220  AddShadow/RemoveShadow/
                                       DrawShadowProj — projected
                                       shadow geometry on terrain.
    [RUST] renderer/objects.rs         objects have a shadow texture,
                                       but there is no shadow-projection
                                       pass over the terrain.
    Observable: ground under static objects shows no drop shadow.
    AP: add a per-group projected shadow pass in terrain.rs after the
    base landscape pass, using the existing shadow textures baked in
    objects.rs. Low priority; match C++ only if we want visual parity.

3. WATER (renderer/water.rs vs MatrixWater.cpp, DrawWater in
         MatrixMap.cpp, BuildWater in MatrixMapGroup.cpp,
         WaterAlpha_t3 in MatrixRenderPipeline.cpp)
==============================================================

3.1 Per-cell wave amplitude
    [C++]  MatrixWater.cpp:185         r[i] randomised per cell around
                                       ~512/2500, giving varied swell.
    [RUST] renderer/water.rs:1233      AMP constant applied uniformly
                                       everywhere.
    Observable: Rust water has a regular, grid-looking ripple; C++
    water has a more organic surface.
    AP: seed a 17x17 amplitude array at startup with the same rand
    distribution as C++, and upload as a small texture or storage
    buffer consumed by the wave shader.

3.2 Sine source: table vs std::f32::sin
    [C++]  MatrixWater.cpp:322-326     SinCosTable[256] lookup indexed
                                       by (angle + phase) & 0xFF.
    [RUST] renderer/water.rs:1238-1239 real f32::sin of TAU * k / 256.
    No visible diff, but quantisation differs (table is only 256
    samples). Not a parity issue.
    AP: none; keep Rust's exact sine.

3.3 Animation time base
    [C++]  MatrixWater.cpp:294-309     integer WATER_TIME_PERIOD = 60 ms
                                       steps; angle advances in whole
                                       ticks.
    [RUST] renderer/water.rs:835-847   float accumulator >= 60.0.
    No observable drift over normal play. Safe.
    AP: none.

3.4 Draw order of alpha vs solid water
    [C++]  MatrixMap.cpp:1743-1789     alpha pass first, then solid pass
                                       (opaque off-map tiles).
    [RUST] renderer/water.rs:880+      solid off-map tiles drawn first,
                                       then in-map fill pipeline.
    Observable: if an on-map translucent quad overlaps an off-map
    solid quad, the final color differs depending on draw order.
    AP: flip the order in water.rs so the alpha (in-map) pass runs
    before the solid (off-map) pass, matching MatrixMap.cpp:1743.

3.5 Camera-space normal reflection UVs
    [C++]  MatrixRenderPipeline.cpp:98, 127  WaterAlpha_t3 uses
                                       D3DTSS_TCI_CAMERASPACENORMAL for
                                       stage 2 mirror texture, with
                                       world scaled by water_scale=12.5
                                       which flattens the normal matrix.
    [RUST] renderer/water.rs (shader)  verify reflection UV path
                                       replicates this exactly.
    AP: inspect the water shader and make sure the mirror UV is
    computed as inverse_transpose(world * view) * normal, with
    world scaled by 12.5 (GLOBAL_SCALE * MAP_GROUP_SIZE / WATER_SIZE).
    If missing or using untransformed normal, fix to match C++.

4.1 Friendly-unit flash

    [RUST] renderer/minimap.rs:1140-1170  flash not implemented.

4.2 Out-of-bounds event arrow markers
    [C++]  MatrixMinimap.cpp:395-425, 645-651  events outside the mini-

    [RUST] renderer/minimap.rs:1160-1171  events clipped but no arrow

    AP: for each out-of-rect event, compute direction from minimap

    [C++]  MatrixMinimap.cpp:800-841   frustum corners drawn as-is.
    [RUST] renderer/minimap.rs:1220-1225  frustum corners clamped to

5. BITMAP / STORAGE / PKG (game/bitmap.rs, assets/*.rs
                         vs CBitmap.cpp, CStorage.cpp, Pack.cpp,
                            CBlockPar.cpp)
==============================================================

5.1 MergeByMask fast paths
    [C++]  CBitmap.cpp:1280-1283       if (m==0) dst=src2; else if
                                       (m==255) dst=src1; else blend.
    [RUST] game/bitmap.rs:43-44        single-formula blend for all
                                       mask values.
    Numerically close but not identical at the extremes because the
    C++ blend uses (a*m >> 8) + (b*(255-m) >> 8), which is not the
    same as (a*m + b*(255-m)) / 255.
    AP: add the two fast-path branches for m==0 and m==255 in
    bitmap.rs to match C++ exactly; keeps atlas construction
    byte-identical with the original tiles.

5.2 MergeWithAlpha precision & channel order
    [C++]  CBitmap.cpp:1334-1373       float alpha blend on BGRA
                                       buffers, with alpha==0 fast
                                       return.
    [RUST] game/bitmap.rs:74-85        integer blend on RGBA buffers,
                                       no fast return.
    Different internal channel order is fine as long as Rust is
    consistent about RGBA throughout; the precision and missing
    alpha==0 fast path can slightly darken overlays.
    AP: (a) add early-return for alpha==0 and alpha==255; (b) use
    (dst*(255-a) + src*a + 127) / 255 rounding to reduce drift vs
    the C++ float blend.

5.3 BlockPar "=<file>" include directive
    [C++]  CBlockPar.cpp:1072-1073     when a block has a from-file
                                       hint, LoadFromTextFile is called
                                       immediately.
    [RUST] assets/blockpar_text.rs:349 from_file stored as Option
                                       but never resolved.
    AP: add a resolution step in the blockpar loader (taking a loader
    callback) that, after parse, walks all entries with from_file set
    and loads/merges them. Without this, any data file relying on
    "=file.btx" semantics will silently be empty.

5.4 CDataBuf element_size sign
    [C++]  CStorage.hpp                element_size is signed int and
                                       can in principle encode negative
                                       sentinels.
    [RUST] assets/storage.rs:41        cast to usize — negative would
                                       wrap to huge positive.
    Shipped data does not seem to use negatives, but the code is
    fragile.
    AP: guard against negative element_size in storage.rs:41 with an
    explicit error (return Err), not a silent cast.

5.5 Pkg accepts ZL02 and ZL03
    [C++]  Pack.cpp:47-59              only "ZL02" magic accepted.
    [RUST] assets/pkg_reader.rs:122-131  accepts both ZL02 and ZL03.
    Harmless, since shipped .pkg contain only ZL02.
    AP: none.

9. FILE LAYOUT — CURRENT vs ORIGINAL
==============================================================

The original tree has three top-level source roots:

  MatrixGame/src/                  game-specific code
    <flat files>                   all Matrix*.{cpp,hpp}
    Effects/                       MatrixEffect*.{cpp,hpp}
    Interface/                     CIFace*, CInterface, MatrixHint, ...
    Logic/                         MatrixAIGroup, MatrixTactics, ...
  MatrixLib/
    Base/         {include,src}/   CBlockPar, CStorage, Pack, CBuf, ...
    Bitmap/       {include,src}/   CBitmap
    3G/           {include,src}/   CCamera, VectorObject, Texture,
                                   ShadowProj, Math3D, ...
    FilePNG/, FileJPG/, Window/, DebugMsg/

Everything in MatrixLib is "engine framework" and everything in
MatrixGame/src is "game-specific". The Rust port currently collapses
most of that into flat renderer/ and game/ modules, which makes it
harder to map a file 1-to-1.

9.2 Divergences from the original layout

D1. Renderer code is mixed with game-logic code
    In the original, MatrixMapGroup.cpp (data layout) is separate from
    MatrixRenderPipeline.cpp (D3D state / stage ops) and from
    MatrixMap.cpp (high-level orchestration). The Rust port fuses all
    three into one big renderer/*.rs file per system (terrain.rs is
    1320 lines, water.rs is 2178 lines, objects.rs is 1664 lines),
    which makes diffs against the original painful.

D2. Engine-vs-game split is lost
    MatrixLib (engine framework) and MatrixGame (game code) are peers
    in the original. In Rust they are merged: CBlockPar, CStorage,
    Pack, CBitmap all live under a thin assets/ + game/bitmap split
    that does not reflect the original library boundary.

D3. "3G" layer is scattered
    MatrixLib/3G provides VectorObject, Texture, CCamera, ShadowProj,
    Math3D. In the Rust port this layer is gone; VectorObject parsing
    lives in game/vo_loader.rs, Texture logic in renderer/texture.rs,
    Camera in renderer/camera.rs, shadow logic is inlined in
    renderer/objects.rs. A reader cannot easily find "the 3G port".

D4. Effects are under-represented
    The original has ~18 MatrixEffect*.cpp files (explosion, flame,
    dust, landscape spot, lightening, shleif, move-to, zahvat, ...).
    The Rust port has only effects/point_light.rs. This is fine for
    now but the layout should leave room for the rest under
    effects/<same_name>.rs.

D5. Interface/ and Logic/ not represented
    No Rust equivalents for Interface/CIFace*.cpp, Interface/
    CConstructor.cpp, Logic/MatrixTactics.cpp, Logic/MatrixAIGroup.cpp,
    etc. That is expected at this port stage, but leaves the layout
    blind to a large amount of upcoming code.

D6. Misc fragments from MatrixGame/src currently "hidden"
    - MatrixFormGame.cpp             -> app.rs               (OK, but renamed)
    - MatrixCursor.cpp               -> (absent)
    - MatrixConfig.cpp               -> (absent)
    - MatrixDebugInfo.cpp            -> (absent)
    - MatrixFlyer.cpp                -> (absent)
    - MatrixLoadProgress.cpp         -> (absent)
    - MatrixLogic.cpp                -> (absent; would belong in game/)
    - MatrixMapTexture.cpp           -> partly in game/map_prepare.rs
                                        and renderer/texture.rs (split)
    - MatrixMapTrace.cpp             -> (absent)
    - MatrixMultiSelection.cpp       -> (absent)
    - MatrixObjectCannon.cpp         -> (absent; folded into objects.rs)
    - MatrixObjectRobot.cpp, MatrixRobot.cpp  -> (absent)
    - MatrixSide.cpp                 -> (absent)
    - MatrixSkinManager.cpp          -> (absent)
    - MatrixSoundManager.cpp         -> (absent; no audio)
    - MatrixTransition.cpp           -> (absent)
    - MatrixVisiCalc.cpp             -> inlined in terrain/water
                                        visibility helpers
    - MatrixSampleStateManager.cpp   -> (absent; wgpu replaces D3D
                                        state manager)
    - DevConsole.cpp                 -> (absent)
    - MatrixInstantDraw.cpp          -> (absent)
    - MatrixShadowManager.cpp        -> partly in objects.rs

Stage 3 — fill in stubs as features arrive (cursor, config, logic,
effects/*, interface/*), each in the file predicted by the target

9.5 Rules of thumb for future file placement

R1. "One MatrixFoo.cpp ↔ one foo.rs" whenever feasible. If the C++
    file is >2000 lines and splits naturally, split in Rust too, but
    use submodules under the same name (map/ with map.rs + submods).
R2. Anything under MatrixLib in the original must live under
    matrix_lib/ in Rust — even if it is one-function-big.
R3. wgpu-only glue (context, bundle, loader) belongs in gfx/, never
    in matrix_game/ or matrix_lib/.
R4. New cross-cutting helpers that have no C++ counterpart (WASM
    bundling, time platform, keybinding) go under platform/ or gfx/
    with a comment saying why there is no C++ file to mirror.
R5. Keep effects/, interface/, logic/ populated with `mod.rs`
    placeholders even before porting starts — makes the layout
    self-documenting.

  L1  Create matrix_lib/{base,three_g}, matrix_game/,

      files for now.
  L2  Move the files listed in Stage 1 into those new modules. This

  L3  Split terrain.rs / water.rs / objects.rs along the original

  L4  Rename app.rs -> matrix_game/form_game.rs and keep a 3-line
